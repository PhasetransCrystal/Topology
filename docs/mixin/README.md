# Mixin 模块内部

面向框架开发者。Mixin 只用于没有公开扩展点的位置，是定点补丁，不是常规扩展方式。

## 职责与边界

- 负责：JEI 配方 GUI、矿脉区块生成、游戏测试服务端静默等无法通过公开 API 完成的最小补丁。
- 不负责：业务逻辑、内容注册、领域扩展。
- 能用公开 API/能力/事件完成的，不使用 mixin。

## 关键类型与数据流

- `JeiRecipeGuiLogicMixin`：JEI 配方 GUI 逻辑。
- `OreChunkGeneratorMixin`：矿脉区块生成。
- `GameTestServerSilencerMixin`：游戏测试服务端静默。

## 为什么这样设计

- 第三方/原版没有扩展点时，mixin 是最后手段。
- 定点补丁比复制/替换整个类风险小，但仍受目标版本影响。
- 把补丁隔离在 `mixin` 包，便于审查与移除。

## 与其他模块的联动

- JEI 集成：GUI 逻辑补丁。
- 矿脉：区块生成补丁。
- 验证：游戏测试环境静默。
- 其他模块不应依赖 mixin 的存在。

## 扩展规范

- 明确目标类、方法、注入点与预期版本；补注入失败时的行为。
- 只改必要逻辑，不扩散到无关方法。
- 优先寻找公开 API/能力/事件；记录为什么不能用。
- 新增/修改 mixin 后至少做启动验证（由开发者手动执行）。

## 常见坑与防止

- 目标方法签名/版本变化：注入失败或行为偏差。
- 用 mixin 改注册流程：应通过领域模块。
- 补丁范围过大：难以维护；缩小注入点。
- 编译通过就认为注入成功：需要启动验证。

# 文档编写规范

面向框架开发者与本地 AI。规定项目细节写到哪里、模块 README 怎么写、单点主题文档怎么拆，以及更新时必须检查什么。

## 三端放置

- `docs-content/`：下游如何使用框架。只写注册入口、钩子、策略、公开契约与兼容边界。
- `docs/`：框架内部细节。每个模块目录以 `README.md` 为入口，主题文档放在模块目录内。
- `demo-docs/`：Demo 如何使用 Topo 能力。写“使用的契约、Demo 组合方式、验收状态”，不写框架契约。
- Obsidian 项目知识库：项目定位、模块地图、证据、出处、验证状态与待核实项；不复制整篇公开契约或内部设计。

## 模块 README 固定结构

每个 `docs/<module>/README.md` 至少包含：

1. **职责与边界**：模块负责什么、不负责什么。
2. **关键类型与数据流**：入口类、注册表、主要阶段。
3. **为什么这样设计**：约束来自哪里，避免哪种错误。
4. **与其他模块的联动**：依赖谁、被谁依赖、跨模块契约。
5. **扩展规范**：新增内容/策略/适配器时的放置位置与步骤。
6. **常见坑与防止**：触发条件、根因、正确做法。
7. **文档**：主题文档与公开契约链接。

## 单点主题文档

- 一个文件只回答一个问题；紧密相连的因果、条件与例外保留在同篇。
- 详细结论、依据和示例放在主题文档，模块 README 只做入口与导航。
- 公开契约不复制到 `docs/`；内部实现不复制到 `docs-content/`；Demo 状态不写成框架状态。
- 事实、推断与待核实项分开写；关键结论附代码路径、版本或核对日期。

## 更新检查

- 相对链接可解析；模块 README 与主题文档互相可达。
- 维护 `docs/README.md` 与 `PROJECT_KNOWLEDGE.md` 的模块入口；不要在索引重复正文。
- 代码事实以源码为准；接口、签名、配置值变化时同步对应文档。
- 区分“代码存在 / 已接线 / 已验收”，不要把编译通过写成运行通过。
